PirateHunter

Платформа подбора ИТ-специалистов с обратной механикой: работодатель

находит кандидата сам. Кандидаты автоматически категоризуются по

объективно подтверждаемому профилю — опрос по специализации, адаптивный

CAT-тест на заявленный грейд (грейд = результат теста, не стаж),

достижения ФСП — и попадают в категоризованную базу (7 специализаций ×

4 грейда). Работодатель описывает потребность, получает объяснимую

подборку («почему этот человек» — разложение score по факторам) и

направляет конкретному кандидату приглашение **с обязательной зарплатной

вилкой**. Контакты кандидата раскрываются только после принятия

приглашения. Достижения ФСП влияют на ранжирование внутри категории,

но не на грейд; кейс «нет истории ФСП» — первоклассный: профиль

показывается со статусом, участвует в подборке без буста.

Кейс ФСП (ЛЦТ 2026, спец. трек). Живой сервис: https://piratehunter.fun.

Репозиторий: https://github.com/PirateThunder/piratehunter

(публичный). Источник правды по

(ARCHITECTURE, RUN, TESTING, VALIDATION, MATCHING, FSP-INTEGRATION, API,

ANTIFRAUD-ATS; единый PDF собирается docs/build_docs.py).

Стек: Python 3.13 · FastAPI · Pydantic v2 · SQLAlchemy 2 (async) ·

Alembic · PostgreSQL 16 ×2 · Redis 7 · numpy (IRT) · LLM Cloud.ru

Evolution (Qwen3.6-35B-A3B, ДЦ РФ; OpenRouter — опция) · Next.js 16

Архитектура PirateHunter

Платформа-агрегатор ИТ-вакансий с обратной механикой: работодатель сам

находит кандидата в категоризованной базе. Четыре сервиса в монорепо,

общение только по HTTP, ноль shared-кода (принципы унаследованы от

проекта piratepitch). Живой сервис: https://piratehunter.fun.

все остальные его эндпоинты — внутренние. См. Caddyfile.

Принципы (PRD §4.2)

  • Ноль shared-кода — сервисы общаются только по HTTP. Frontend знает

только backend; backend знает core-api и fsp_registry. Ни один сервис

не импортирует код другого.

  • Свои PG + Redis у backend и hunter_core — независимые релизы и

миграции (Alembic у backend).

  • core-api и fsp_registry наружу не выставлены — Caddy их не

проксирует; в dev-compose порты опубликованы на 127.0.0.1 только

для отладки и смоука.

  • ПДн только в backend (privacy by design, аргумент для 152-ФЗ):

ФИО, телефон, контакты, согласия живут в ph_back и никуда не

уходят. core-api получает и хранит лишь анонимный candidate_id и

оценочный снапшот. fsp_registry хранит синтетические достижения без

ПДн; привязка fsp_id ↔ candidate_id — только в backend.

  • Детерминированные fallback везде: LLM-фичи (парсинг потребности,

перефразировка заданий) работают и без ключа/сети — демо не зависит

от внешних API.

Соответствие 152-ФЗ и data residency

Контур целиком развёрнут в юрисдикции РФ — **трансграничной передачи

персональных данных нет ни на одном участке**:

УчастокГде исполняетсяКомментарий
Хостинг стендаVPS, ЦОД РФ (Selectel)docker compose + Caddy, данные на дисках в РФ
LLM-контурCloud.ru Evolution Foundation Models (Qwen/Qwen3.6-35B-A3B), ЦОД РФserverless у российского облачного провайдера; HUNTER_LLM_PROVIDER=cloudru
Мок-реестр ФСП / OIDCвнутри docker-сети стендасинтетика, без ПДн; боевой провайдер заменяется конфигом
ПДн (ФИО, телефоны, контакты, согласия)только backend (ph_back)в core-api уходят лишь candidate_id и оценочный снапшот

Дополнительно: согласия пользователей фиксируются при онбординге

(consent_pd, consent_publish), контакты кандидата скрыты до accept

(§7.6), есть анонимный режим карточки. Смена LLM-провайдера — конфигом

(HUNTER_LLM_PROVIDER=openrouter|cloudru), код не меняется.

Потоки данных

Оценочный снапшот (backend → core-api)

После каждого изменения профиля (тест пройден, ФСП привязан/отвязан,

профиль обновлён) backend пушит в core:

PUT /internal/snapshots/{candidate_id}
{candidate_id, spec, grade_verified, theta, test_score, fsp_score,
 stack[], updated_at}

test_score: null = «вычисли сам из θ». Матчинг читает только

снапшоты — подборка не дёргает backend и не видит ПДн.

Результат подборки (core-api → backend)

POST /internal/match возвращает ranked `[{candidate_id, score,

explanation, in_category}]` → backend джойнит с профилями (ph_back),

применяет правила видимости (контакты скрыты до accept) и отдаёт фронту.

Кандидаты вне категории идут отдельным блоком «рядом с запросом»

(in_category=false).

ФСП (backend → fsp_registry)

Backend по fsp_id запрашивает GET /fsp/v1/profiles/{fsp_id},

считает fsp_score (формула — MATCHING.md), кэширует в Redis

(TTL 3600 с) и включает в снапшот. 404 = нет истории →

fsp_score = 0, блок достижений не показывается (обязательный кейс ТЗ).

Тест (backend → core-api, проксирование)

Frontend ходит на POST /api/v1/tests/sessions и

POST /api/v1/tests/sessions/{id}/answers; backend проксирует в

core-api /internal/tests/... с подстановкой candidate_id, возвращает

вопрос/результат. Состояние сессии CAT живёт в ph_core.

Вход через FSP ID (redirect-цепочка)

Backend /api/v1/auth/fsp/authorize отдаёт authorize_url на

browser-facing адрес реестра (BACK_FSP_PUBLIC_URL, login_hint как

у OIDC); реестр 303-ит браузер на BACK_FSP_REDIRECT_URI = GET-callback

backend'а на origin фронта (Next проксирует /api/* — refresh-cookie

ph_refresh ставится на домен фронта); backend обменивает

code→token→userinfo и 303-ит на /login/callback, сессию поднимает

bootstrap через /auth/refresh. Подробно — FSP-INTEGRATION.md.

Доменная модель (кратко, полная — PRD §5)

  • backend (ph_back): User, AuthCode, CandidateProfile (ФИО,

контакты, стек, согласия 152-ФЗ), GradeState (кулдауны), Company,

Need (потребность), Vacancy, Invitation (обязательная вилка ЗП),

Application. Инвариант ТЗ: salary_from/to NOT NULL, from ≤ to,

salary_type обязателен (gross/net подписан в UI).

  • hunter_core (ph_core): ItemTemplate (параметризованный шаблон:

генератор экземпляра по seed + детерминированный чекер), TestSession,

Answer, AssessmentSnapshot (единственное, что читает матчинг),

BetaStat (калибровка сложности).

  • fsp_registry: stateless детерминированный генератор

FspProfile(fsp_id, rating, ranks, contests, events); БД не нужна.

Стек

Python 3.13 + FastAPI + Pydantic v2 + SQLAlchemy 2 (async) + Alembic,

pytest, ruff; numpy для IRT-математики; LLM — **Cloud.ru Evolution Foundation

Models** (Qwen3.6-35B-A3B, ДЦ в РФ — контур 152-ФЗ; смена провайдера —

конфигом HUNTER_LLM_PROVIDER: openrouter | cloudru) с детерминированным

fallback. Frontend: Next.js

16.3.1 (App Router, React Compiler), Bun, Tailwind v4, Base UI,

2. Запуск и развёртывание

Запуск и развёртывание PirateHunter

Живой сервис: https://piratehunter.fun. Инфраструктура: Docker +

docker-compose + Caddy (авто-TLS). Вся система поднимается одной

командой на чистой машине.

Локальный запуск (docker compose)

Требования: Docker с плагином compose, ~4 ГБ свободной RAM.

cp .env.example .env        # 1. секреты/конфиг (дефолты рабочие для dev)
docker compose --env-file .env up -d --build   # 2. всё: 4 сервиса + PG×2 + Redis
./scripts/seed.sh           # 3. эталонные демо-данные (302 кандидата, 16 компаний, …)

Проверка health:

curl localhost:64844/health    # backend
curl localhost:51457/health    # core-api
curl localhost:52457/health    # fsp-registry
curl localhost:56151/          # frontend
curl localhost:52457/fsp/v1/profiles/fsp_001   # синтетический профиль ФСП (или 404)

OpenAPI backend — https://api.piratehunter.fun/docs (живой Swagger на

проде) или локально http://localhost:64844/docs (при BACK_ENV=local).

Вход по email-коду: без SMTP код пишется в лог backend

(docker compose logs -f backend, поле dev_code). При

BACK_AUTH_DEV_LOGIN=1 (dev-дефолт) на /login — кнопка входа

демо-аккаунтами без почты: candidate, candidate-fsp, employer.

Порты в dev опубликованы на 127.0.0.1: 56151 (frontend), 64844

(backend), 51457 (core-api), 52457 (fsp-registry), 55432/55433 (PG),

56379 (Redis) — для отладки и смоука.

Скрипты scripts/

Воспроизводимый цикл: reset-dev.sh → smoke.sh (зелёный) → seed.sh.

Деплой на VPS (prod)

Целевой стенд: VPS 2 vCPU / 4 ГБ RAM, Ubuntu + Docker + compose-плагин.

В рантайме стек потребляет ~1.5 ГБ — VPS намеренно **не собирает

образы** (сборка Next.js и pip/uv-зависимостей не влезла бы в RAM и

заняла бы десятки минут): образы собираются на домашней машине и

переносятся готовыми.

Подготовка (один раз)

  1. DNS: A-записи piratehunter.fun (и www.) → IP VPS. Для

мок-OIDC — поддомен fsp-id.piratehunter.fun → тот же IP.

  1. На VPS:

```bash

ufw allow 80,443/tcp && ufw enable # Caddy выпускает TLS (HTTP-01)

# ssh-ключ, docker, compose-плагин

git clone <repo> piratehunter && cd piratehunter

cp .env.example .env # прод-значения (см. ниже)

```

Прод-.env (отличия от dev)

BACK_ENV=prod                 # /docs закрыт

NEXT_PUBLIC_DEV_LOGIN=0
BACK_JWT_SECRET=<длинная случайная строка>

# SMTP (коды на почту): BACK_SMTP_HOST/PORT/USER/PASSWORD/FROM

В Caddyfile заменить piratehunter.example.com → piratehunter.fun

и раскомментировать блок fsp-id.* (мок-OIDC наружу). Важно:

Caddyfile примонтирован файлом — после правок

docker compose ... up -d --force-recreate caddy.

Перенос образов и старт

# На домашней машине (сборка):
docker compose --env-file .env build
docker save $(docker compose --env-file .env config --images) | \
  ssh vps 'docker load'

# На VPS:
docker compose --env-file .env up -d     # без --build: образы уже загружены
docker compose ps                        # все healthy
./scripts/seed.sh                        # эталонные демо-данные

Caddy сам выпускает и продлевает сертификаты Let's Encrypt (HTTP-01,

порты 80/443), редиректит HTTP→HTTPS, проксирует сайт на frontend, а

/api/v1 — на backend. core-api наружу не торчит (PRD §4.2).

4. E2E браузерные проверки фронта

Фронт (Next.js 16, FSD) проверяется в браузере по сквозному сценарию

PRD §1: лендинг → логин (email-код / «Войти через FSP ID» / dev-кнопка)

→ онбординг кандидата → адаптивный тест с таймером → экран категории →

ЛК работодателя: потребность → «мы поняли так» → подборка с панелью

«Почему в подборке» → приглашение с вилкой → инбокс кандидата с вилкой

крупно → accept → раскрытие контактов. Проверяются money-экраны PRD

§7.11 (подборка с explanation и виджетом «вилка vs рынок», тест,

Что осознанно не автоматизировано

пользователей, подборка < 2 c на 300+ кандидатах по снапшотам).

4. Валидация

Валидация решения (PRD §9)

Собственная процедура валидации (ТЗ §2, критерий «Тестирование +

валидация + категоризация», 25%). Эталонных датасетов нет — построен

синтетический контур: синтетические агенты-кандидаты с известным

истинным уровнем, ручная разметка набора «потребность × кандидаты».

Харнесс — CLI в hunter_core/validation/, артефакты прогона —

hunter_core/out/validation/.

Методология

Синтетические агенты (§9.1). Агент с истинным уровнем θ_true

отвечает верно с вероятностью P = σ(θ_true − β) по логистической

модели IRT (β — сложность шаблона), плюс шум по времени ответа. Агенты

равномерно покрывают шкалу θ. Контрольный прогон: **60 агентов × 2

повторных теста**, режим full (10 вопросов), специализация backend,

банк [28, 28] шаблонов по повторам, seed 42. Дополнительно выполнен

полный прогон 300 агентов × 3 повтора (итоги ниже).

Метрики (§9.2).

  1. Стабильность: повторные тесты агента → % точного совпадения грейда, % в пределах ±1 грейда.
  2. Дискриминативность: монотонность медиан присвоенного θ по полосам θ_true; Spearman(θ_true, θ_est); confusion-матрица; путаница соседних грейдов.
  3. Эквивалентность экземпляров: для каждого шаблона разброс доли верных ответов по 50 seeds — доля seeds вне 95% биномиального ДИ (проверка, что параметризация по seed не меняет сложность).
  4. Калибровка β: сходимость BetaStat (метод моментов по доле верных с поправкой на θ ответивших, демпфирование) к эмпирической сложности.
  5. Релевантность подбора: ручная разметка 20 пар «потребность × 50 кандидатов» → Precision@5, nDCG@10.
  6. Пересечение наборов заданий между сессиями (антислив, Jaccard).

Пороги приёмки (§9.3) — зафиксированы до прогона

5. Механика подбора

Механика подбора (PRD §7.5)

Критерий «Механика подбора» — 35% оценки. Подбор — внутри core-api,

работает только по оценочным снапшотам (privacy by design, PRD §4.3);

backend применяет фильтры до скоринга и правила видимости после.

Формула скоринга

score = 0.40·test_score + 0.30·stack_match + 0.20·fsp_score + 0.10·freshness

Реализация: hunter_core/engine/scoring.py (match_score), веса —

DEFAULT_WEIGHTS (конфигурируемы).

Обоснование порядка весов. Подтверждённая тестом компетентность

(0.40) важнее самоописанного стека (0.30): грейд присваивается только

адаптивным тестом (Q&A 07.10), стек — декларация кандидата. Достижения

ФСП (0.20) — верифицированный внешний сигнал, усиливают ранжирование

внутри категории, но не влияют на грейд (обязательное правило Q&A).

Свежесть (0.10) — мягкий буст активных профилей, чтобы выдача не

застаивалась.

Факторы

test_score (0.40)

Позиция θ внутри θ-полосы грейда: (θ − lo) / (hi − lo), кламп 0..1.

Полосы: intern [−4, −1), junior [−1, 0.5), middle [0.5, 2), senior

[2, 4]. В снапшоте может прийти готовое значение (test_score: null =

вычисли из θ).

Unverified-потолок 0.4. Кандидат без подтверждённого грейда

показывается со статусом «не подтверждён» и опускается в выдаче

(потолок test_score = 0.4), но не скрывается — иначе выпадает из

оборота (Q&A 06.10). Реализация — UNVERIFIED_CAP = 0.4,

explanation помечает «(не подтверждён — потолок 0.4)».

stack_match (0.30)

Σ w(совпавший навык): совпадение по must весит ×3, nice ×1;

нормировка 3·|must| + |nice| к 0..1; регистронезависимо; пересечение

must∩nice считается must. Пустые требования → 0.0 (нет сигнала, а не

штраф). Совпадение — точное по тегам стека снапшота.

fsp_score (0.20)

Считается backend'ом по достижениям ФСП (PRD §7.9, критерии — по Q&A

06.10/07.10), в core приходит готовым в снапшоте:

ДостижениеВес
Победитель (1 место)1.0
Диплом I–III степени0.7
Призовое место (4–10)0.5
Участие (11+)0.15
Мероприятие (роль/эксперт)0.05
  • Дисциплины и уровни соревнований не ранжируются — «все

соревнования равно важны» (Q&A 06.10). Считаем результативность и

число.

  • Антифарм-затухание явками: i-е участие даёт ×0.5^(i−1) к весу

участия (0.15, 0.075, 0.0375, …), мероприятия — аналогично. Защита

от набивания профиля одними онлайн-явками. Результативные достижения

(1.0/0.7/0.5) затуханию не подвержены.

  • Cap 1.0. Нет истории ФСП → 0, штрафа сверх веса нет.
  • Командные результаты учитываются как обычные достижения (вклад честно

не выделить — Q&A). Давность не штрафуем (архива на 2–4 года нет).

  • Опционально post-MVP (заложено в модель): небольшой бонус за

релевантность дисциплины специализации кандидата.

freshness (0.10)

Экспоненциальное затухание от последней активности (тест / задание /

обновление профиля): 0.5^(days / 30) — полураспад 30 дней. Нет данных

об активности → 0.0.

Конвейер подборки (POST /internal/match)

  1. Фильтры работодателя (spec, grade, стек, «есть ФСП») — до

скоринга (PRD §7.5.2).

  1. Снапшоты специализации сплитятся:
  • Категория (in_category=true): grade_verified есть и

≥ требуемому грейду. Скоринг полной формулой, сортировка по score.

  • «Рядом с запросом» (in_category=false): грейд ниже

требуемого или не подтверждён — те же снапшоты, тот же score, но

отдельным блоком после категории. Категорийность не ломается,

находчивость добавляется.

  1. core + near, top-limit (default 20), детерминированный тай-брейк

по candidate_id.

  1. Backend джойнит профили, применяет видимость контактов (только после

accept) и отдаёт фронту.

Ранжирование внутри категории (§7.5.4)

GET /internal/category/{spec}/{grade}/ranking — тот же score в режиме

просмотра категории без потребности: stack-фактор заменяется

нейтральной константой NEUTRAL_STACK_VALUE = 0.5 (его вклад 0.30·0.5

одинаков для всех — не влияет на порядок, честно отражён в explanation:

«стек: нейтральная константа»). Выше оказываются сильнее подтверждённые

(θ в полосе) профили с достижениями ФСП — формулировка ТЗ §2.

Объяснимость (§7.5.3) — обязательный артефакт

Каждая строка выдачи несёт explanation — разложение по 4 факторам в

порядке весов: {factor, weight, value, contribution, human_text}.

Примеры human_text:

  • «тест: грейд middle, θ=1.20 → 0.47»
  • «стек: совпало must 4/5, nice 2/3 → 0.76»
  • «достижения ФСП: суммарный счёт 0.72»
  • «свежесть профиля: активность 3 дн. назад → 0.93»

Фронт рендерит панель «Почему в подборке» — прямое попадание в критерий

«обоснованность ранжирования и объяснимость выдачи».

Рыночная аналитика вилок (§7.5.5)

Раз ЗП обязательна и прозрачна (ТЗ §2.2.1), принцип превращён в фичу:

GET /api/v1/employer/market/salary?spec&grade — виджет «вилка vs

рынок по категории». Агрегат по данным платформы (анонимно):

перцентили p25/p50/p75 границ вилок потребностей (sample_needs) и

приглашений (sample_invitations) категории spec×grade + размер

категории из core (category_size). Пустая выборка → перцентили null,

  1. Работодатель видит «ваша вилка ниже медианы backend×middle» до

отправки приглашения. Стоимость реализации — один SQL-агрегат.

Схема «потребность → подборка → приглашение»

  1. Работодатель описывает потребность свободным текстом →

LLM-парсинг POST /internal/llm/parse-need (`{spec, grade,

stack_must, stack_nice, confidence, notes}`; детерминированный

keyword-fallback без ключа; невалидные slug'и → null) → экран «мы

поняли так» с правкой → подтверждённая структура идёт в матчинг.

  1. Shortlist: match по снапшотам → ranked + explanation + блок

«рядом с запросом».

  1. Приглашение конкретному кандидату: текст + **обязательная вилка

ЗП** (salary_from/to + salary_type gross/net) + способ связи;

вакансия опциональна (ТЗ §2.2). Без вилки — 422.

  1. Кандидат видит вилку до ответа; статусы

sent → viewed → accepted | declined; после accept контакты

раскрываются обеим сторонам.

6. Интеграция с ФСП

Интеграция с ФСП (мок-реестр + мок-OIDC «FSP ID»)

Сервис fsp_registry играет двойную роль (Q&A 06.10): **мок-реестр

достижений участника ФСП** (контракт GET /fsp/v1/profiles/{fsp_id})

и мок-провайдер входа «FSP ID» (имитация OAuth/OIDC-флоу). После

хакатона мок заменяется боевым реестром/Keycloak — backend не меняется,

меняется только конфиг. Это «схема предполагаемой интеграции» из ТЗ

§3.4, исполненная в коде.

Контракт реестра достижений

GET /fsp/v1/profiles/{fsp_id}
→ 200 {fsp_id, rating, ranks[{discipline, rank, date}],
       contests[{name, discipline, date, place, diploma 1|2|3|null,
                 team, team_result{team_name, place}}],
       events[{name, date, role}]}
→ 404 — истории ФСП нет

Детерминированный генератор (fsp_registry/app/profiles/service.py):

seed = sha256(соль + fsp_id) — один и тот же fsp_id всегда даёт один

и тот же профиль, в том числе между перезапусками. По хэшу **~60%

fsp_id имеют историю, ~40% → 404** (пользователь без истории —

обязательный кейс ТЗ). Распределение результатов: ~20% победители с

дипломом I–III, ~25% призовые места 4–10, остальные участники; ~35%

командных; рейтинг, разряды (0–3 дисциплины), мероприятия (0–4).

Поле level (regional/national) сознательно не заводим — эксперты

против ранжирования дисциплин и уровней (§7.9). Сервис stateless, БД

не нужна. ПДн не хранит — «человекочитаемость» обеспечивает backend

(у себя маппинг fsp_id → candidate_id).

Мок-OIDC flow входа «FSP ID»

Контракт приближен к OIDC, чтобы переезд на боевой Keycloak был

конфигом. Эндпоинты fsp_registry:

МетодПутьНазначение
GET/oidc/authorize?client_id&redirect_uri&state&login_hintавторизация: автовыбор демо-личности или явный fsp_id; 303 на redirect_uri с code+state
POST/oidc/token (form)обмен кода: {access_token, id_token, expires_in} — self-contained JWT HS256
GET/oidc/userinfo (Bearer){sub=fsp_id, name, email}
GET/.well-known/openid-configurationdiscovery (issuer = browser-facing адрес)

Коды одноразовые, in-memory с TTL; client_id валидируется,

redirect_uri — по allowlist; обмен привязан к паре code+redirect_uri

+client_id (повторный обмен → invalid_grant).

Redirect-цепочка (как это проходит в браузере)

  1. Фронт: GET /api/v1/auth/fsp/authorize?fsp_id=… → backend отдаёт

{authorize_url} — browser-facing адрес реестра

(BACK_FSP_PUBLIC_URL), OIDC-параметрами (client_id,

redirect_uri, state, login_hint = fsp_id).

  1. Браузер идёт на /oidc/authorize → реестр 303-ит на

BACK_FSP_REDIRECT_URI = GET-callback backend'а на origin фронта

(https://piratehunter.fun/api/v1/auth/fsp/callback?code&state) —

Next проксирует /api/*, поэтому refresh-cookie ph_refresh

ставится на домен фронта.

  1. Backend валидирует одноразовый state (Redis, TTL 600 с), обменивает

code → token → userinfo у реестра, создаёт/находит User по

fsp_id, подтягивает достижения, 303-ит браузер на

/login/callback.

  1. Сессия поднимается bootstrap-ом: /api/v1/auth/refresh по

ph_refresh-cookie → access в память (zustand), single-flight

refresh в ky.

  1. POST-вариант callback (code+state в теле) оставлен для API-клиентов.

Сквозной флоу покрыт смоуком (шаг 11): authorize_url → 303 (code+state)

→ callback → 303 /login/callback → cookie → refresh → users/me с

fsp_id=fsp_001.

Кейс «404 = нет истории ФСП» (обязательный по ТЗ)

  • Привязка ФСП ID (автоматически при входе через FSP ID или вручную в

настройках): fsp_registry вернул 404 → fsp_score = 0, блок

достижений не рендерится, UI подсказывает «привяжите ФСП ID».

  • Кандидат полностью не скрывается: показывается со статусом,

участвует в подборке с unverified-потолком test_score (0.4), если

грейд подтверждён — в категории на общих основаниях.

  • Фильтр работодателя «есть достижения ФСП» корректно исключает таких

кандидатов.

  • Путь покрыт тестами backend (FSP-привязка с 404, «404 = нет истории →

score 0, блок отсутствует»); ручная демонстрация — демо-аккаунт

candidate (без ФСП) против candidate-fsp (fsp_001 — богатая

история). Достижения кэшируются в Redis (TTL 3600 с).

Критерии влияния достижений (Q&A 06.10 / 07.10)

  • Достижения ФСП — буст внутри грейда (фактор fsp_score, вес 0.20),

на грейд не влияют: грейд присваивается только тестом.

  • Дисциплины равны, уровни соревнований не ранжируются.
  • Антифарм: затухание повторных явок ×0.5^(i−1); cap 1.0.
  • Командный результат — как обычное достижение; давность не штрафуем.
  • Формула и веса — в MATCHING.md; бонус за релевантность дисциплины

специализации — опционально post-MVP (модель discipline заложена).

Замена мока на боевой Keycloak — конфигом

Backend ходит к провайдеру через интерфейс IdentityProvider

(провайдеры fsp-id и email-code); клиент мок-OIDC параметризован:

BACK_FSP_PUBLIC_URL=https://fsp-id.piratehunter.fun   # issuer/authorize
BACK_FSP_REGISTRY_URL=http://fsp-registry:52457       # внутри сети
BACK_FSP_REDIRECT_URI=https://piratehunter.fun/api/v1/auth/fsp/callback
BACK_FSP_CLIENT_ID / BACK_FSP_CLIENT_SECRET           # client-конфиг

Переезд: поднять Keycloak с realm ФСП, завести client

(piratehunter-backend), поменять три env — код backend'а не трогаем

(claims mapping: sub → fsp_id, standard OIDC). Реестр достижений

заменяется боевым API с тем же контрактом ответа (200/404).

Формат ошибок

Единый стиль: HTTP-код + JSON { "detail": "человекочитаемое описание" }.

  • 422 — валидация схемы (Pydantic, тело с деталями полей) или

доменная валидация (нет вилки, неизвестный slug специализации);

  • 401/403 — нет токена / чужой ресурс или роль не подходит

(зависимости FastAPI: кандидат не видит чужие приглашения,

работодатель не видит контакты до accept);

  • 404 — ресурс не найден (включая «нет истории ФСП» у реестра);
  • 409 — конфликт состояния: смена грейда в кулдауне, ФСП ID уже у

другого аккаунта;

  • 429 — лимиты (коды на email, приглашения);
  • 502 — core-api недоступен;
  • 500 — { "detail": "внутренняя ошибка: <Type>: <msg>" } (глобальный

handler, без стека наружу).

ATS-сценарий (roadmap-концепция ТЗ)

По определению из ответов 07.10: ATS = «синхронизация вакансий,

откликов и статусов с внутренней системой найма работодателя через API,

чтобы платформа встраивалась в существующий процесс, а не требовала

ручного дублирования». Концепция (в MVP не реализуем, схема зафиксирована):

  1. Работодатель заводит API-ключ в кабинете; аутентификация

X-API-Key (argon2-хэш ключа, паттерн известен).

  1. Синхронизация вакансий: POST /api/v1/employer/vacancies из ATS

(или полный обмен по webhook-эндпоинтам ATS).

  1. Статусы: webhooks платформы по смене статусов приглашений/откликов

(sent → viewed → accepted/declined) + маппинг на типовые этапы

ATS-воронки (screening → interview → offer).

Полная проработка — защита от недобросовестных работодателей (модель

угроз, что уже в MVP и что в roadmap) и интеграция с ATS (сценарии,

подписи вебхуков, идемпотентность, примеры) — в

ANTIFRAUD-ATS.md.

Публичный OpenAPI (живой): https://api.piratehunter.fun/docs —

можно открыть и потрогать прямо из Swagger UI.

Roadmap API

  • MCP-сервер для ИИ-агентов: инструменты «описать потребность →
