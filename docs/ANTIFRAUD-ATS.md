# Защита от недобросовестных работодателей и интеграция с ATS

Концепция закрывает два необязательных пункта ТЗ §6.6: «проработанная
концепция защиты от фиктивных вакансий» и «интеграция с ATS», а также
фиксирует мобильный адаптив (третий пункт критерия). Всё, что помечено
✅, **уже работает в коде и проверяется** (ссылки на шаги смоука).

## 1. Модель угроз

| Угроза | Последствие |
|---|---|
| Спам-приглашения (массовые, нерелевантные) | отток кандидатов, потеря доверия |
| «Резюме-майнинг»: сбор контактов без намерения найма | утечка персональных данных |
| Фиктивные вакансии/потребности (без условий, для рекламы) | мусор в базе, репутация платформы |
| Боты и скрейперы базы | нагрузка, утечка профилей |
| Дискриминационные/оскорбительные тексты | юридические риски |

## 2. Что уже реализовано в MVP

- ✅ **Контакты кандидата скрыты до принятия приглашения** — главный барьер
  против резюме-майнинга: без accept работодатель не получает ни email, ни
  телефон (правило §7.6, проверяется шагами 8 и 10 смоука: `contacts: null`).
- ✅ **Обязательная ЗП-вилка** — приглашение без вилки отклоняется (422):
  «фиктивная вакансия без условий» не проходит по конструкции (шаг 9 смоука).
- ✅ **Лимит приглашений — 100/час на компанию** (NFR §12): защита от
  массового спама одним аккаунтом.
- ✅ **Вход только через подтверждённую идентичность** (email-код или
  FSP ID) — анонимный аккаунт создать нельзя; роли и согласия фиксируются
  при онбординге (аудируемость).
- ✅ **Наблюдаемость поведения**: статусы приглашений
  (sent → viewed → accepted/declined) — база для репутационных метрик.
- ✅ **ПДн только в backend**: тест-движок и реестр оперируют анонимным
  `candidate_id` — даже при компрометации внутреннего сервиса ПДн не утекают.

## 3. Roadmap антифрода (приоритет сверху вниз)

1. **Верификация компании**: подтверждение домена e-mail, ИНН,
   ручная модерация первых 3 приглашений (очередь модерации).
2. **Репутационный счёт компании**: доля принятых приглашений, доля
   ответов на сообщения, жалобы кандидатов; при низком score — понижение
   компании в выдаче и предупреждение кандидатам.
3. **Жалоба кандидата в один клик** (спам / нерелевантно / оскорбление) →
   автоматическая приостановка компании при N жалоб за окно.
4. **Rate-limit по IP и аккаунту** (Redis уже в контуре) + CAPTCHA при
   аномалиях регистрации.
5. **Анти-бот сигналы**: скорость просмотра карточек, паттерн приглашений,
   fingerprint устройства.
6. **LLM-модерация текстов приглашений** (оскорбления, дискриминация) —
   провайдер уже в контуре (Cloud.ru, ДЦ РФ, 152-ФЗ).
7. **Аудит-лог действий работодателя** (что смотрел/отправлял/когда) +
   выгрузка для разбора инцидентов.
8. **Для вакансий (§7.7)**: проверка дублей (хэш/эмбеддинги), обязательные
   условия, срок жизни, авто-архив.
9. **Дашборд антифрода**: доля жалоб, отвалов, аномальные аккаунты.

## 4. Интеграция с ATS — концепция

Принцип: платформа — **источник верифицированных грейдов и категорий**;
ATS работодателя остаётся его системой учёта. Обмен — через открытый
REST API (OpenAPI уже публикуется backend'ом; см. `docs/API.md`).

Сценарии:

- **a) Вакансии/потребности из ATS → платформа.** `POST /api/v1/employer/needs`
  (в roadmap §7.7 — `POST /vacancies`): маппинг полей, идемпотентность по
  `external_id` (повторный POST с тем же id не создаёт дубль).
- **b) События платформы → ATS (webhooks).** `invitation.sent`,
  `invitation.accepted`, `invitation.declined`, `test.completed`,
  `grade.verified` — POST на callback-URL работодателя с подписью
  HMAC-SHA256 (`X-Signature`), ретраи с экспоненциальной паузой,
  dead-letter после N попыток.
- **c) Синхронизация статусов.** Маппинг: `sent → screening`,
  `viewed → screening`, `accepted → interview`, `declined → rejected`;
  обратная синхронизация — `PATCH /employer/invitations/{id}` (roadmap).
- **d) Выгрузка верифицированного профиля в карточку ATS**: грейд
  (подтверждён тестом + дата), θ, стек, достижения ФСП, ссылка на PDF-профиль
  (`GET /candidate/profile/pdf` — уже реализован).

Машинная авторизация: **API-ключи со scope** (roadmap; сейчас — JWT +
refresh-cookie), rate-limit на ключ, версионирование `/api/v1`.

Пример (уже работающий контур):

```bash
# работодатель: разобрать свободный текст вакансии в структуру (LLM)
curl -X POST https://piratehunter.fun/api/v1/employer/needs/parse \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"raw_text":"Ищем middle backend: Python, FastAPI, PostgreSQL, 250-400к"}'

# подборка с объяснением по каждому кандидату
curl https://piratehunter.fun/api/v1/employer/needs/$NEED_ID/shortlist \
  -H "authorization: Bearer $TOKEN"
```
