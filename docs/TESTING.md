# Тестирование PirateHunter

Покрытие трёх слоёв: (1) юнит- и API-тесты каждого сервиса на pytest,
(2) живой сквозной смоук `scripts/smoke.sh` по HTTP по поднятому
docker-стеку, (3) браузерные E2E-проверки фронта. Плюс воспроизводимый
цикл «reset → smoke → seed» и детерминированные сиды.

## 1. Автотесты (pytest)

Цифры — фактические прогоны `pytest -q` в каждом сервисе (11.10.2026):

| Сервис | Тестов | Как гоняются | Что покрывают |
|---|---|---|---|
| hunter_core | **75** | чистый pytest, без сети и БД | CAT-движок (θ-обновление, стоп-правила, исходы confirmed/upgrade/downgrade), скоринг и explanation, fsp_score, стек-матчинг, свежесть, каталог, фабрики шаблонов (генерация экземпляров + чекеры), валидационный харнесс |
| backend | **110** | pytest + aiosqlite, core/fsp клиенты мокаются без сети | auth (email-код, dev-login, refresh-cookie), роли и зависимости, профили, правила видимости контактов (скрыто до accept), приглашения (вилка обязательна — 422 без неё), снапшоты в core, FSP-привязка (включая 404 «нет истории»), кулдауны грейда (409), каталог, рынок вилок, резюме |
| fsp_registry | **17** | чистый pytest | детерминированный генератор профилей (~60/40 история/404), мок-OIDC (authorize → code → token → userinfo, одноразовость кода, TTL, невалидный client/redirect) |

Итого **202 теста**, все зелёные. Запуск:

```bash
cd backend       && uv run pytest -q && uv run ruff check .
cd hunter_core   && uv run pytest -q && uv run ruff check .
cd fsp_registry  && uv run pytest -q && uv run ruff check .
```

Фронт: `cd frontend && bun run lint && bun run build` (biome + tsc +
прод-сборка Next.js). Кейс «404 = нет истории ФСП» в живом контуре
проверяется вручную демо-аккаунтом `candidate` (см. FSP-INTEGRATION.md).

Точечные приёмы: backend гоняется на aiosqlite (паттерн piratepitch) —
миграции и репозиторный слой без поднятия PG; core/fsp клиенты
подменяются фейками, внешних вызовов в тестах нет.

## 2. Живой сквозной смоук — scripts/smoke.sh

17 шагов по реальному стеку (`docker compose up`), каждый — HTTP-вызов
с проверкой результата (`curl` + `jq`), стоп по первому FAIL:

1. **Health всех сервисов** — backend/core-api/fsp-registry `/health` + frontend `/` и `/login`.
2. **Dev-login** — демо-аккаунты `candidate-fsp` (кандидат с ФСП) и `employer`, получение JWT.
3. **Email-код** — `auth/email/request` → `dev_code` (при `BACK_ENV=local` без SMTP) → `auth/email/verify` → токен.
4. **Профиль кандидата** — PUT `/candidate/profile` (стек, специализация, заявленный грейд, контакты).
5. **CAT-тест через backend → core-api** — старт сессии на middle, цикл ответов до результата `{theta, grade_verified, outcome}`.
6. **Компания + потребность** — PUT `/employer/company`, POST `/employer/needs` (backend проксирует LLM-парсинг «мы поняли так»).
7. **Shortlist** — GET `/employer/needs/{id}/shortlist`: непустая подборка, у каждой строки есть `explanation`.
8. **Скрытость контактов** — наш кандидат в банке, `contacts: null` до accept (privacy-правило §7.6).
9. **Приглашение** — без вилки → **422**; с вилкой 250–350k gross → 201 (инвариант ТЗ).
10. **Accept** — кандидат: до accept контакты компании скрыты, после accept раскрываются **обеим** сторонам (кандидат видит HR-контакты, работодатель — email кандидата).
11. **Полный OIDC-флоу «FSP ID»** — redirect-цепочка: `authorize_url` → 303 реестра (code+state) → GET-callback на origin фронта → 303 на `/login/callback` с refresh-cookie `ph_refresh` → `/auth/refresh` → access; `users/me` подтверждает `fsp_id=fsp_001`.
12. **LLM-парсинг потребности** — `needs/parse` распознаёт «мидла на FastAPI, PG, Redis» → spec=backend, grade=middle (работает и без ключа — детерминированный fallback).
13. **Экспресс-режим теста (для жюри)** — mode=express завершается ≤ 4 вопросов, `mode=express` в результате.
14. **Рынок вилок** — `market/salary?spec=backend&grade=middle`: медиана по потребностям и приглашениям платформы (p50 from=250000, to=350000 на эталонном сиде).

Финал: «СМОУК ПРОЙДЕН — все 17 шагов зелёные».

## 3. Воспроизводимость

```bash
./scripts/reset-dev.sh   # чистые схемы ph_back/ph_core, стек переподнят, health зелёный
./scripts/smoke.sh       # 17 шагов — зелёные
./scripts/seed.sh        # эталон piratehunter-v1: 302 кандидата / 16 компаний / 6 потребностей / 40 приглашений
```

Сиды детерминированы (seed `piratehunter-v1`), датасет воспроизводим
побайтово — перед защитой и после тестов жюри база возвращается к
эталонному состоянию одной командой.

## 4. E2E браузерные проверки фронта

Фронт (Next.js 16, FSD) проверяется в браузере по сквозному сценарию
PRD §1: лендинг → логин (email-код / «Войти через FSP ID» / dev-кнопка)
→ онбординг кандидата → адаптивный тест с таймером → экран категории →
ЛК работодателя: потребность → «мы поняли так» → подборка с панелью
«Почему в подборке» → приглашение с вилкой → инбокс кандидата с вилкой
крупно → accept → раскрытие контактов. Проверяются money-экраны PRD
§7.11 (подборка с explanation и виджетом «вилка vs рынок», тест,
приглашение, категория). Кабинеты фазы 1 на моках
(`NEXT_PUBLIC_API_MOCK=1`), auth — всегда живая.

## Что осознанно не автоматизировано

Песочница исполнения code-заданий и прокторинг — плюс, не MVP (Q&A
06.10); code-шаблоны заложены в модель, при нехватке времени выкидываются
без потери баллов. Нагрузочное тестирование не требуется оценкой (десятки
пользователей, подборка < 2 c на 300+ кандидатах по снапшотам).
