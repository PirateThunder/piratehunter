# PRD — PirateHunter: платформа подбора ИТ-специалистов с обратной механикой

Статус: черновик для реализации. Код не писать до утверждения документа.

Кейс: ФСП «Цифровая платформа-агрегатор ИТ-вакансий с верифицированным
профилем достижений участника ФСП» (ЛЦТ 2026, спец. трек). Полный разбор
ТЗ — в разделе [Соответствие ТЗ](#13-соответствие-тз). Исходники кейса —
`materials/` (ТЗ pdf, брендбук, шаблон презентации; не в git).

Продукт: веб-платформа, где **работодатель находит кандидата сам** —
кандидаты автоматически категоризуются по объективно подтверждаемому
профилю (опрос + тест на заявленный грейд + достижения ФСП), а работодатель
описывает потребность, получает объяснимую подборку и направляет конкретному
человеку приглашение **с обязательной зарплатной вилкой**. Контакты
кандидата раскрываются только после принятия приглашения.

Наследование: архитектура, стек, инфраструктура и подход к сдаче повторяют
`~/Projects/piratepitch` (монорепо, сервисы только по HTTP, ноль
shared-кода, свои PG/Redis у сервисов, внутренние API наружу не выставлены,
taskiq-фоновики, Caddy + compose, `deliverables/` + PRD как источник
правды). Сознательные отличия — в §4.4.

Двойное назначение документа: (1) план победы на хакатоне — приоритеты
жёстко следуют весам жюри (механика подбора 35%, тестирование/валидация
25%); (2) фундамент стартапа «hh с человеческим лицом» — пост-хакатон
roadmap (автоотклики, ATS-оптимизация резюме, AI-скрининг) влияет на
архитектурные решения уже сейчас (§17).

## 1. Обзор

Два ролевых кабинета. Сквозной сценарий (= сценарий демо для жюри, ТЗ §3.3):

```
КАНДИДАТ:  регистрация (email + код) → профиль/резюме (форма или PDF)
           → опрос по специализации → выбор заявляемого грейда
           → адаптивный тест → присвоение категории (spec × грейд)
           → [привязка ФСП ID → подтянуты достижения]

РАБОТОДАТЕЛЬ: регистрация → профиль компании → описание потребности
           (свободный текст + структура) → распознанный запрос
           → подборка: категории + кандидаты с объяснением «почему»
           → приглашение конкретному кандидату (текст + вилка ЗП)

СХОДИМОСТЬ: кандидат видит приглашение с вилкой → принимает
           → контакты раскрываются обеим сторонам
```

Дополнительно (желательно, не обязательно по ТЗ): публикация вакансий и
самостоятельный отклик кандидата; регулярные короткие задания от
работодателей, поддерживающие профиль актуальным.

Сервисы (порядок = порядок разработки, §14):

```
backend  (FastAPI)  — auth, профили, ПДн, вакансии, приглашения, отклики
hunter_core (FastAPI, internal) — тест-движок (CAT), матчинг, валидация
fsp_registry (FastAPI) — мок-реестр достижений ФСП + адаптер интеграции
frontend (Next.js)  — лендинг + оба ЛК одним приложением (FSD)
```

Ключевой принцип владения данными: **ПДн живут только в backend**;
hunter_core оперирует анонимными `candidate_id` и снапшотами оценки
(грейд, θ, fsp_score) — privacy by design, аргумент для 152-ФЗ в
документации и на питче.

## 2. Цели и критерии успеха

Цель хакатона — максимум баллов при жёстком лимите времени. Веса жюри
(ТЗ §6) превращаем в бюджет усилий:

| Критерий | Вес | Что делаем | Где |
|---|---|---|---|
| Механика подбора | 35% | Объяснимый скоринг, сценарий «потребность → подборка → приглашение», e2e без сучков | §7.5, §7.6 |
| Тестирование + валидация + категоризация | 25% | Параметризованные шаблоны + адаптивный тест + скрипт валидации с цифрами | §7.4, §9 |
| Интерфейс | 10% | Аккуратный UI в гамме ФСП, понятный путь в обоих ЛК | frontend |
| Питч | 10% | Шаблон ЛЦТ, демо по §3.3 ТЗ, цифры валидации | deliverables |
| Тех. проработка | 7% | OpenAPI, тесты, compose one-liner, чистый код | §12, §15 |
| Доп. функционал | 7% | Вакансии + отклики; регулярные задания; концепции антифрода и ATS | §7.7, §7.8, §17 |
| Полнота + документация | 6% | Все обязательные пункты ТЗ §3.4, обработка «нет истории ФСП» | §13, deliverables |

Нефункциональные критерии успеха:

- `docker compose up -d --build` поднимает всё одной командой на чистой
  машине; жюри проходит сквозной сценарий без нашей помощи.
- Валидация даёт числа, которые не стыдно показать (пороги — §9.3).
- Ни одного критичного требования ТЗ не потеряно (чек-лист §13 зелёный).

## 3. Технологический стек

Повторяет piratepitch; отклонения обоснованы.

### 3.1. Backend и внутренние сервисы

- Python 3.13, uv, FastAPI, Pydantic v2, SQLAlchemy 2 (async), Alembic.
- PostgreSQL 16 (отдельный инстанс/БД на сервис), Redis 7, taskiq
  (фоновые: парсинг резюме, пересчёт снапшотов, регулярные задания).
- Auth: JWT (access + refresh), email-код как у piratepitch
  (`request → verify`), argon2 для паролей API-ключей; dev-login локально.
- OpenAPI из коробки FastAPI; публичный референс — Scalar (как в
  piratepitch).
- PDF: извлечение текста — pypdf; генерация стандартизированного
  PDF-профиля — HTML-шаблон + weasyprint.
- Тесты: pytest (aiosqlite для юнитов backend по паттерну piratepitch),
  ruff.

### 3.2. hunter_core

- Тот же Python-стек. Плюс: numpy для IRT-математики, sqlite in-memory
  для sandbox-проверки SQL-заданий, subprocess-сandbox с лимитами
  (time/mem) для проверки кода (MVP: только Python-задания с кодом).
- CLI (`uv run python ...`) для валидационного харнесса и сидов — по
  паттерну CLI-first из piratepitch.

### 3.3. Frontend

- Next.js (App Router), React, Bun, Tailwind v4, Base UI (shadcn-паттерн),
  zustand, ky, biome — как в piratepitch, архитектура FSD.
- Одно приложение: лендинг + ЛК кандидата + ЛК работодателя (роль после
  логина). Адаптив — опционально (ТЗ: «опционально для MVP»).
- **Айдентика ФСП — точные токены**, извлечены из выкачанного
  fsp-russia.ru (`~/Downloads/Websites/fsp-russia.ru`, Bitrix) и брендбука
  (`materials/брендбук/`):

  | `ink` | `#1B1C21` | заголовки, основной текст |
  | `ink-2` | `#2D2E37` | текст, тёмные элементы |

### 3.4. LLM-контур

Письменные ответы организаторов 07.10 (§18.3): **облачные LLM
допустимы, в том числе зарубежные**; жёсткого пула нет, «предпочтительнее
открытые модели с адекватным числом параметров». Если в модель уходят
ПДн — риски 152-ФЗ/трансгранички на команде. Использование обязательно
описать в документации: какие модели, как и зачем (MODELS-раздел,
паттерн piratepitch).

- AIClient по паттерну piratepitch (реализован в `hunter_core/llm/`):
  провайдеры за интерфейсом; **для сдачи — Cloud.ru Evolution Foundation
  Models** (Qwen/Qwen3.6-35B-A3B, serverless, ДЦ в РФ: персональные
  данные в LLM-контуре не покидают юрисдикцию — 152-ФЗ), openrouter —
  опциональная альтернатива. Смена провайдера/модели — конфигом
  (`HUNTER_LLM_PROVIDER`, `HUNTER_LLM_MODEL`), без правок кода.
- Применения (все — с детерминированным fallback, система работает и без
  LLM — демо не зависит от сети и ключей):
  1. Разбор PDF-резюме в структуру профиля (fallback: пустая форма).
  2. Парсинг потребности работодателя из свободного текста (fallback:
      keyword-матчинг по справочнику).
  3. Подсказка заявляемого грейда по резюме (разрешена Q&A, §7.2).
  4. Перефразировка оболочек заданий (fallback: шаблон как есть).
- **ПДн в LLM-запросы не отправляем** (проектное решение, не вынужденная
  мера): резюме перед разбором обезличивается (вырезаем ФИО/контакты),
  в потребности ПДн нет. Этим полностью снимаем риск 152-ФЗ/
  трансгранички при любом провайдере — compliance-аргумент для защиты.

## 4. Архитектура

### 4.1. Диаграмма

```
        Браузер
           │ same-origin /api/* (rewrites)
           ▼
┌────────────────────┐        ┌──────────────────────────────────┐
│  frontend :56151   │ ─────► │           backend :64844          │
│  Next.js (FSD)     │        │  /api/v1 (JWT) · PG · Redis ·     │
└────────────────────┘        │  taskiq · ПДн · контакты          │
                              └───┬──────────────┬────────────────┘
                                  │ HTTP         │ HTTP
                    (внутр. docker-сеть, наружу не выставлены)
                                  ▼              ▼
                    ┌──────────────────┐  ┌───────────────────────┐
                    │ core-api :51457  │  │ fsp_registry :52457   │
                    │ тесты · матчинг  │  │ мок-реестр ФСП        │
                    │ PG · Redis       │  │ (адаптер интеграции)  │
                    └──────────────────┘  └───────────────────────┘
```

### 4.2. Принципы (унаследованы)

- **Ноль shared-кода** — сервисы общаются только по HTTP. Frontend знает
  только backend; backend знает core-api и fsp_registry.
- **Свои PG + Redis** у backend и hunter_core — независимые релизы.
- **core-api и fsp_registry наружу не выставлены** (внутренняя сеть).
- **ПДн только в backend**: core получает/хранит лишь `candidate_id` и
  оценочный снапшот; fsp_registry хранит синтетические достижения без ПДн
  (привязка `fsp_id ↔ candidate_id` — в backend).

### 4.3. Потоки данных

- **Оценочный снапшот** (`AssessmentSnapshot`): backend после изменений
  (тест пройден, ФСП привязан, профиль обновлён) пушит в core:
  `{candidate_id, spec, grade_verified, theta, test_score, fsp_score,
  stack[], updated_at}`. Матчинг читает только снапшоты — подборка не
  дёргает backend.
- **Результат подборки**: core возвращает ranked `[{candidate_id, score,
  explanation}]` → backend джойнит с профилями, применяет правила
  видимости (контакты скрыты) и отдаёт фронту.
- **ФСП**: backend по `fsp_id` запрашивает достижения у fsp_registry,
  считает `fsp_score` (формула §7.9) и включает в снапшот. 404 = нет
  истории → `fsp_score = 0`, блок достижений не показывается (обязательный
  кейс ТЗ).

### 4.4. Сознательные отличия от piratepitch

- Нет VK-бота и VK Mini App (не требуется кейсом); auth — мок-вход через
  FSP ID (ожидаемый сценарий по Q&A, §7.1) + email-код + dev-login.
  Боевой Keycloak не поднимаем (Q&A: «не ждут»), совместимость — через
  `IdentityProvider` и OIDC-подобный мок в fsp_registry.
- Никакого импорта вакансий со сторонних площадок (Q&A: «не нужен и
  нежелателен») — платформа связывает только своих работодателей и
  соискателей.
- Нет пайплайна стадий с resume — вместо него сессионный тест-движок
  (state в PG core, не в файловом workdir).
- Публичный API (`/public/v1` + ключи) в MVP **не делаем**, но
  версионируем `/api/v1` и держим auth-слой готовым к нему (задел на
  стартап, §17) — дешёво, так как паттерн известен.

## 5. Доменная модель

Состав полей — минимальный рабочий набор; детали уточняются в коде.

### 5.1. backend (PG `ph_back`)

- `User(id, email, role: candidate|employer, is_verified, created_at)`
- `AuthCode(email, code_hash, expires_at)` — вход по коду.
- `CandidateProfile(user_id, fio, phone, contacts jsonb, stack text[],
  spec_slug, grade_claimed, experience_years, roles text[], soft_skills
  text[], about, resume_text, fsp_id null, privacy jsonb, consent_pd bool,
  consent_publish bool, updated_at)`
- `GradeState(candidate_id, grade_verified null, theta null, last_test_at,
  grade_changed_at null, status: unverified|confirmed|upgrade_offer|
  downgrade_offer)` — кулдауны считаются от `grade_changed_at`.
- `Company(user_id, name, description, industry, contacts jsonb, site)`
- `Need(id, company_id, raw_text, parsed jsonb, stack_must text[],
  stack_nice text[], spec_slug, grade, salary_from, salary_to, created_at)`
- `Vacancy(id, company_id, title, description, stack text[], spec_slug,
  grade, salary_from, salary_to, salary_type: gross|net, status:
  draft|published|archived, created_at)` — опциональная фича.
- `Invitation(id, company_id, candidate_id, vacancy_id null, text,
  salary_from, salary_to, salary_type: gross|net, contact_method,
  status: sent|viewed|accepted|declined, created_at, status_at)` —
  привязка к вакансии **не обязательна** (ТЗ §2.2).
- `Application(id, vacancy_id, candidate_id, cover_text, status:
  sent|viewed|accepted|rejected, created_at)` — опциональная фича.
- `RegularTask(id, company_id, spec_slug, text, reference_answer null,
  created_at)` + `RegularTaskAnswer(id, task_id, candidate_id,
  answer_text, score null, scored_by: system|employer null,
  created_at)` — опциональная фича.

Инвариант ТЗ §2.2: `salary_from`/`salary_to` обязательны (NOT NULL,
валидация `from ≤ to`, рубли) в `Vacancy` и `Invitation`; `salary_type`
обязателен и подписан в UI (Q&A 06.10: гросс или нетто непринципиально,
лишь бы явно).

### 5.2. hunter_core (PG `ph_core`)

- `ItemTemplate(id, spec_slug, topic, grade_band, type: mcq|code|sql,
  beta float, payload jsonb, version, active)` — параметризованный шаблон:
  генератор экземпляра по seed + чекер. `payload` для mcq: варианты
  генерации кода/вопроса; для code: сигнатура, ген. тестов, эталон;
  для sql: ген. схемы/данных, эталонный запрос.
- `TestSession(id, candidate_id, spec_slug, grade_target, theta, se,
  asked template_ids[], seeds[], status, started_at, finished_at)`
- `Answer(session_id, template_id, seed, correct bool, elapsed_ms,
  theta_after)`
- `AssessmentSnapshot(candidate_id PK, spec_slug, grade_verified, theta,
  test_score, fsp_score, stack text[], updated_at)` — единственное, что
  читает матчинг.
- `BetaStat(template_id, beta, n_answers)` — калибровка сложности по
  истории ответов (§7.4.5).

### 5.3. fsp_registry (мок FSP ID + реестр, синтетика)

Двойная роль (Q&A 06.10): мок-реестр достижений **и** мок-провайдер
входа «FSP ID» (имитация OAuth/OIDC-флоу для §7.1).

- `FspProfile(fsp_id PK, rating int, ranks jsonb[{discipline, rank,
  date}], contests jsonb[{name, discipline, date, place, diploma:
  1|2|3|null, team bool, team_result null|{team_name, place}}],
  events jsonb[{name, date, role}])` — состав по Q&A: места, разряды,
  дисциплины, командные результаты. Поле `level` (regional/national/…)
  **не заводим**: эксперты против ранжирования дисциплин (§7.9).
- ПДн не хранит; «человекочитаемость» достижений обеспечивает backend
  (у себя маппинг fsp_id → кандидат).
- Для входа: эндпоинты authorize/token/userinfo-заглушки (минимальный
  OIDC-подобный флоу на своих данных; «боевых доступов не будет,
  имитации достаточно», Q&A).

## 6. Справочник специализаций и грейдов

Справочник свой (ТЗ это прямо разрешает), в коде — единый
`catalog.py` в core, backend тянет по HTTP и кэширует. Q&A 06.10:
«отрасль» из ТЗ = IT-направление (бэкенд, фронтенд, ML, аналитика), не
индустрия; несколько специализаций на MVP не обязательны — наш набор
избыточен достаточно, чтобы жюри могло проверить решение.

**Специализации MVP (7):** `backend`, `frontend`, `fullstack`, `mobile`,
`qa` (вкл. automation), `devops`, `data-ml`. Глубина банка по
письменным ответам 07.10: «достаточно 2 специализаций × 2 грейда, если
весь путь работает; широта справочника оценку не поднимает, механика
важнее» → глубокая проработка только `backend` (полная: mcq+sql),
средняя `frontend`/`qa` (mcq), остальные — минимальный пул.
Дизайнеров в справочник MVP не включаем (07.10: приоритет техническим
ролям с объективным тестированием; объективный тест для дизайнеров —
отдельный плюс-челлендж, вне нашего scope).

**Грейды (4):** `intern`, `junior`, `middle`, `senior` — это **уровни
навыков, подтверждаемые тестом, а не стаж в годах** (письменный ответ
07.10; «официально» грейд присваивается только по результату
тестирования). Стаж остаётся атрибутом профиля, в определение грейда
не входит. Lead/архитектор — post-MVP.

**Категория** = `spec_slug × grade_verified` (например `backend × middle`
= «бэкенд-разработчики с опытом»). Более детальная модель (стек, роль,
формат) не требуется — наш stack-фактор в скоринге уже плюс (07.10).
У кандидата в MVP одна категория; несколько категорий — плюс, бэклог
(07.10). Кандидат без подтверждённого грейда — категория
`spec × unverified`; по Q&A 06.10: **показываем со статусом
«не подтверждён» и опускаем в выдаче, полностью не скрываем** (иначе
кандидат выпадает из оборота). Реализация опускания — срезанный потолок
`test_score` (§7.5.2).

## 7. Функциональные требования

### 7.1. Auth и роли

- **Вход через FSP ID — ожидаемый сценарий** (Q&A 06.10: «имитировать
  стоит», возможно станет обязательным критерием): кнопка «Войти через
  FSP ID» ведёт на мок-OIDC флоу fsp_registry (§5.3) — authorize →
  код → токен → профиль (fsp_id, достижения). Backend создаёт/
  находит User по fsp_id, достижения подтягиваются сразу. На боевом
  Keycloak потом меняется только base_url и client-конфиг.
- Регистрация по email с подтверждением (ТЗ §2.2.4) — альтернативный
  канал (Q&A: «альтернативную регистрацию по email тоже можно
  имитировать»): `POST /api/v1/auth/email/request` → код на почту (без
  SMTP — код в лог бэкенда, флоу проходит локально) → `verify` →
  JWT-пара. Роль выбирается при первом входе.
- Чекбоксы при регистрации: согласие на обработку ПДн (152-ФЗ),
  отдельно — на публикацию профиля работодателям.
- `IdentityProvider`-интерфейс: провайдеры `fsp-id` (мок, сейчас) и
  `email-code`; боевой Keycloak — третьим провайдером сменой конфига
  (claims mapping задокументировать). Реальный Keycloak в Compose не
  поднимаем (Q&A: «не ждут»).
- Ограничения доступа (ТЗ): кандидат видит только свои приглашения и
  отклики; работодатель не видит контакты до accept. Проверки — на
  уровне зависимостей FastAPI + сериализаторов, тесты на оба запрета.

### 7.2. ЛК «Кандидат»

- Профиль: форма (ФИО, контакты, стек, грейд, роли, стаж, софт-скиллы)
  **или** загрузка PDF → LLM-разбор → предзаполненная форма (правится
  вручную). Генерация стандартизированного PDF-профиля (бренд ФСП,
  weasyprint) — кнопка «Скачать».
- Онбординг-визард: опрос (специализация, направление) → выбор
  заявляемого грейда → тест (§7.4) → экран «Ваша категория» с историей.
  Выбор грейда — самостоятельный (обязательно по Q&A), но показываем
  **подсказку рекомендуемого грейда** по разобранному резюме (Q&A:
  «подсказка по резюме допустима») — LLM/эвристика по стажу и стеку.
- Категория и грейд: текущий статус, история тестов, кнопки «пройти на
  грейд ниже/выше» с учётом кулдауна (показываем дату доступности).
- Приглашения: список входящих (компания, текст, **вилка ЗП**, способ
  связи), принять/отклонить; после accept — экран с раскрытыми контактами
  (наши — работодателю, компании — нам).
- Вакансии (опц.): общий список опубликованных, отклик, мои отклики и
  статусы.
- Регулярные задания (опц.): входящая задача от работодателя → «решить /
  предложить подход» → результат вливается в `freshness` профиля.
- Настройки: приватность (что видно: ФИО/стек/достижения; **опциональный**
  анонимный режим «Кандидат #id» — по письменному ответу 07.10 ФИО и
  места работы показывать допустимо, ТЗ закрывает только контактные
  данные, поэтому анонимность — выбор кандидата, не дефолт), согласия,
  привязка ФСП ID.

### 7.3. ЛК «Работодатель»

- Профиль компании: название, описание, направление, контакты.
- Потребность: свободный текст + структура (стек, специализация, грейд).
  LLM-парсинг показывает «мы поняли так» с возможностью поправить — сам
  экран продаёт «умность» системы.
- Подборка: по потребности — рекомендованные категории и кандидаты;
  карточка кандидата = профиль (ФИО и опыт видны — 07.10; скрыты только
  контакты) + **панель «Почему в подборке»** (разложение score по
  факторам, §7.5.3). Фильтры и уточнение запроса без потери подборки
  (URL-state + сохранённые потребности).
- Банк кандидатов: вся база, фильтры: специализация, грейд, категория,
  стек, наличие достижений ФСП.
- Выход на контакт: форма приглашения (текст, вилка ЗП — обязательна,
  способ связи; привязка к вакансии опциональна) → трекер статусов
  (отправлено/просмотрено/принято/отклонено). После accept — раскрытие
  контактов кандидата.
- Вакансии (опц.): CRUD, публикация, входящие отклики, смена статусов.

### 7.4. Механика тестирования (core) — критерий 25%

Проблема ТЗ: фиксированный банк разойдётся по рынку; чистая LLM-генерация
не гарантирует сопоставимую сложность и объективность. Решение —
**параметризованные шаблоны + адаптивное тестирование (CAT-lite)**.

#### 7.4.1. Параметризованные шаблоны

Задание = шаблон + seed. Шаблон задаёт семейство задач **фиксированной
сложности** с генератором уникальных экземпляров и детерминированным
чекером. Типы:

- `mcq`: «что выведет код» / «какой результат выражения» — фрагмент кода
  параметризуется (значения, структура, порядок веток), варианты ответов
  генерируются из тех же параметров (правильный + правдоподобные
  дистракторы из типовых ошибок).
- `code`: мини-функция; параметризованные входные данные и скрытые тесты;
  проверка — запуск в sandbox (subprocess, лимиты 2 c / 128 МБ, MVP —
  Python). **Деприоритизировано** (Q&A 06.10: «песочница — плюс, хватает
  адаптивного опросника и задач с разбором решений»): делаем после mcq/
  sql, при нехватке времени выкидываем без потери баллов.
- `sql`: параметризованная схема и наполнение (sqlite in-memory),
  проверка сравнением результата с эталонным запросом (set-equality).
- Опция (Q&A): задачи прошлых соревнований ФСП как дополнительный буст —
  только с защитой от преимущества уже решавших (не входят в основной
  тест; отдельный маркер «спортивная задача»). Не MVP.

Каждый кандидат получает **уникальные экземпляры** (seed = session-scoped):
пересказ чужого варианта бесполезен — числа/схемы/код другие.
LLM-перефразировка оболочки (текст легенды) опциональна и не влияет на
параметры и проверку — сопоставимость сложности сохраняется.

**Фабрики шаблонов (снижение стоимости банка).** Главный риск банка —
трудоёмкость авторства (§15). Митигация: часть шаблонов порождается
*мета-генераторами* — кодом, который сам синтезирует шаблоны с
автовычисленным ответом. Пример: фабрика `mcq`-трейсинга собирает случайный
фрагмент Python из безопасных конструкций (списки, срезы, dict-comprehension,
замыкания) по грамматике, вычисляет вывод интерпретатором, генерирует
дистракторы из типовых мутаций (off-by-one, перепутанный порядок) → готовый
верифицированный шаблон без авторской работы. Аналогично фабрика SQL:
случайная схема из библиотеки доменов + эталонный запрос по шаблону
JOIN/GROUP BY. Цель: ≥ 50% банка — из фабрик, авторская работа только на
тематическое покрытие. Каждый шаблон (любого происхождения) проходит
sanity-чек §10. Это же усиливает §7.4.4: банк пополняется машинно, а не
руками — «разошедшиеся» задания заменяются партиями.

#### 7.4.2. Адаптивный тест (CAT-lite)

- Шкала θ (способность) и β (сложность шаблона), логистическая модель
  `P(correct) = σ(θ − β)`.
- Старт: θ = медиана полосы заявляемого грейда; вопросы покрывают темы
  специализации round-robin; следующий шаблон — argmax информации
  (β ближайшая к θ) из неиспользованных.
- После каждого ответа: обновление θ (ограниченный шаг, затухающий K),
  пересчёт SE. Стоп: 10 вопросов **или** SE < 0.35 (ранняя уверенность).
- **Экспресс-режим для жюри** (Q&A 06.10: «экспресс-тест на 3–5 минут
  подойдёт, но должна быть возможность самим пройти тесты»): конфиг
  длины — полный (10 вопросов) / экспресс (4 вопроса, те же полосы θ,
  пониженная точность честно оговорена в результате). Жюри проходит
  пилот и пороги грейдов само — прохождение обязано быть приятным и
  быстрым. Демо-режим допустим (Q&A).
- Таймлимит на вопрос (mcq 90 c, code 8 мин, sql 4 мин) — против
  гугления/списывания, фиксируется `elapsed_ms` (сигнал в валидацию).

#### 7.4.3. Исходы и грейд

Полосы θ (калибруются валидацией, дефолт): intern < −1 ≤ junior < 0.5 ≤
middle < 2 ≤ senior.

- θ в полосе заявляемого грейда или выше (без запаса на следующий) →
  `confirmed`: грейд подтверждён, категория присвоена.
- θ ≥ порог следующего грейда + margin → `upgrade_offer`: предлагаем тест
  на повышение (ТЗ: «справившийся уверенно может повысить»).
- θ < полосы → `downgrade_offer`: грейд **не понижается принудительно**;
  предлагаем тест на уровень ниже; до подтверждения категория —
  `spec × unverified` (§6).
- Кулдауны (сроки — наш выбор, ТЗ и Q&A разрешают): смена подтверждённого
  грейда — не чаще раза в **90 дней**; повтор теста на текущий грейд —
  не чаще **30 дней** (антиперебор); первичный тест — сразу. **Провал и
  уход на грейд ниже — без сжигания попытки** (Q&A): `downgrade_offer` →
  тест на уровень ниже не запускает кулдаун смены грейда, кулдаун
  стартует только от фактического подтверждения нового грейда. Всё в
  конфиге; логика описывается в документации (Q&A: «логику надо описать
  и обосновать»).

#### 7.4.4. Устойчивость к распространению (для документации)

1. Уникальные экземпляры по seed → «слитый» вариант не совпадает ни с
   чьим.
2. Пул шаблонов × темы × ротация → пересечение наборов двух сессий
   минимально; метрика пересечения считается в валидации (§9).
3. Таймлимиты + адаптивность → списывание дороже собственного решения.
4. Версии шаблонов (`version`, `active`) → скомпрометированный шаблон
   гасится без остановки системы.

#### 7.4.5. Калибровка сложности

`BetaStat`: после каждых N ответов на шаблон β сдвигается к эмпирической
сложности (метод моментов по доле верных ответов с поправкой на θ
ответивших; демпфирование, границы). Заявленная сложность со временем
заменяется измеренной — аргумент «объективность» для жюри.

### 7.5. Механика подбора (core) — критерий 35%

#### 7.5.1. От потребности к запросу

LLM (fallback — keyword) извлекает из `raw_text`: `spec_slug`, `stack_must`,
`stack_nice`, `grade`, ожидания. Работодатель подтверждает/правит —
подтверждённая структура идёт в матчинг.

#### 7.5.2. Скоринг

```
score = 0.40·test_score + 0.30·stack_match + 0.20·fsp_score + 0.10·freshness

test_score  = позиция θ внутри полосы грейда + бонус за подтверждённость
              (unverified — срезанный потолок 0.4: показываем со статусом
              «не подтверждён» и опускаем в выдаче, НЕ скрываем — Q&A)
stack_match = Σ w(совпавший навык), must весят ×3, нормировка к 0..1
fsp_score   = §7.9 (нет истории → 0, штрафа сверх веса нет)
freshness   = exp-decay от последней активности (тест/задание/обновление)
```

Веса — в конфиге core; в документации — обоснование порядка весов
(подтверждённая компетентность важнее самоописанного стека). Грейд
задаётся только тестом; достижения ФСП влияют на ранжирование внутри
категории, но не на грейд (Q&A, обязательное правило). Фильтры
работодателя применяются до скоринга; кандидаты вне категории, но с
сильным профилем, — отдельным блоком «рядом с запросом» (не ломает
категорийность, добавляет находчивости).

#### 7.5.3. Объяснимость (обязательный артефакт UI)

Каждый результат несёт `explanation`: список факторов с вкладом
(«тест middle подтверждён θ=1.2 → +0.33»; «стек: совпало 4/5 must →
+0.24»; «диплом II степени, чемпионат ФСП 2026 → +0.18»). Фронт
рендерит панель «Почему в подборке». Это прямое попадание в критерий
«обоснованность ранжирования и объяснимость выдачи» и отличный слайд.

#### 7.5.4. Ранжирование внутри категории

Тот же score в режиме просмотра категории (без потребности):
`stack_match` заменяется нейтральной константой, выше — сильнее
подтверждённый профиль + достижения ФСП (формулировка ТЗ §2).

#### 7.5.5. Рыночная аналитика вилок (усиление дифференциатора)

Раз ЗП обязательна и прозрачна (ТЗ §2.2.1), превращаем принцип в фичу:
на экранах потребности/приглашения/вакансии показываем виджет **«вилка
vs рынок по категории»** — медиана и квартили зарплатных ожиданий
категории по данным платформы (агрегация приглашений и вакансий,
анонимно; в MVP — по синтетическим данным §10). Работодатель видит
«ваша вилка ниже медианы backend×middle» до отправки приглашения —
прямая демонстрация ценности прозрачности обеим сторонам и готовый
слайд на питч. Стоимость реализации — один SQL-агрегат.

### 7.6. Приглашения и правила видимости

- Создание: обязательны текст, `salary_from/to`, способ связи; вакансия
  опциональна (ТЗ §2.2.2). Валидация на уровне схемы и БД.
- Статусы: `sent → viewed → accepted | declined`; `viewed` ставится при
  первом открытии кандидатом; обе стороны видят актуальный статус.
- Видимость контактов кандидата: сериализатор backend отдаёт
  `contacts` только если `invitation.status == accepted` **или** есть
  `Application` от этого кандидата этой компании. Тест на оба пути.
- Кандидат видит вилку ЗП и условия **до** ответа — принципиальное
  отличие сервиса (ТЗ §2.2.1), подчеркнуть в UI и на питче.

### 7.7. Вакансии и отклики (+7%, ✅ РЕАЛИЗОВАНО 11.10)

- CRUD вакансий (вилка ЗП обязательна), публикация/архив; статусы
  draft→published→closed, `external_id` — ATS-идемпотентность.
- Кандидат: список опубликованных с фильтрами, отклик с сопроводительным
  (404 не-published, 409 повтор), «мои отклики» и статусы. Работодатель:
  входящие отклики с контактами откликнувшегося (он инициировал контакт),
  смена статусов viewed|invited|rejected; при `invited` кандидат видит
  контакты компании (симметрия §7.6).
- UI: отдельные вкладки «Вакансии»/«Мои отклики» у кандидата и раздел
  «Вакансии» у работодателя; проверки — `scripts/smoke.sh` шаги 15–17.

### 7.8. Регулярные задания (опционально)

- Работодатель сам пишет короткую задачу на специализацию (Q&A: «задания
  пишет работодатель»); система раз в N дней (конфиг, дефолт 14)
  предлагает подходящим кандидатам «решить / предложить подход»
  (taskiq-рассылка по расписанию). Работодатель может предложить задание
  точечно кандидату или выложить на общее обозрение (Q&A).
- Проверка (Q&A): если у задания есть `reference_answer` — проверяет
  система (автосравнение); открытый ответ (скрипт, бизнес-решение)
  оценивает сам работодатель (`scored_by: employer`).
- Ответ хранится; +к `freshness`; работодатель видит ленту ответов —
  «свежий сигнал о кандидате» из ТЗ.
- Из того же Q&A-блока в бэклог (плюсы, не MVP): внутренний чат
  платформы, отзыв доступа к контактам после раскрытия, поддержка
  15–17 лет (согласие родителей на ПДн), прокторинг/антиплагиат.

### 7.9. ФСП-интеграция

- `fsp_registry` — мок-реестр (своя модель достижений, §5.3) за
  HTTP-адаптером `GET /fsp/v1/profiles/{fsp_id}` + мок-вход FSP ID
  (§7.1). После хакатона мок заменяется реальным реестром/Keycloak —
  backend не меняется. Это и есть «схема предполагаемой интеграции» из
  ТЗ §3.4, исполненная в коде.
- Привязка: автоматическая при входе через FSP ID (§7.1) или вручную в
  настройках (ввод ФСП ID → fetch → карточка достижений: рейтинг,
  разряды, дипломы, места, командные результаты, мероприятия).
- `fsp_score` — по правилам Q&A 06.10: **дисциплины и уровни
  соревнований не ранжируем** («все соревнования равно важны, внутренний
  рейтинг "чемпионат выше хакатона" давать не советуют»). Считаем
  результативность и число: победитель 1.0 / призёр (диплом I–III) 0.7 /
  призовое место 0.5 / участие 0.15 / мероприятие 0.05; сумма с
  затуханием за повторные явки (i-е участие даёт ×0.5^(i-1) к весу
  участия — защита от набивания профиля одними онлайн-явками, Q&A),
  cap 1.0. Командный вклад не выделяем — учитываем командный результат

### 7.10. Резюме: разбор и генерация

## 9. Валидация решения (собственная процедура, ТЗ §2 + критерий 2)

Датасетов и эталонной разметки нет — делаем синтетический контур и сами
его размечаем. По Q&A 06.10: формального минимума по объёму выборки и
независимой экспертной оценке нет, реальных кандидатов привлекать не
обязательно, достаточно эталонной разметки команды. **Жюри проверяет
руками на своём закрытом наборе синтетических профилей** (воспроизводимость
и разделяющая сила грейдов), пилот и пороги грейдов проходит само —
поэтому экспресс-режим §7.4.2 и чистое прохождение теста «чужим»
человеком — часть валидационной поверхности. Харнесс — CLI в
`hunter_core/validation/`, результаты и графики —
`deliverables/validation/` (таблицы + png). Набор пар
«вакансия–кандидат» (§9.2.5) собираем сами и **описываем в документации**
(состав, разметка, результаты) — Q&A: «свой набор + описание».

### 9.1. Синтетические агенты-кандидаты

Агент с истинным уровнем `θ_true` отвечает верно с `P = σ(θ_true − β)`
(+ шум по `elapsed`). 300 агентов: равномерно θ_true ∈ [−2.5, 3.5].

### 9.2. Метрики

1. **Стабильность**: 3 повторных теста на агента → % совпадения
   присвоенного грейда; % в пределах ±1 грейда.
2. **Дискриминативность**: медиана присвоенного θ по полосам θ_true —
   монотонность; confusion-матрица «истинный × присвоенный» грейд.
3. **Эквивалентность экземпляров**: для каждого шаблона разброс доли
   верных ответов по 50 seeds — внутри биномиального ДИ (проверка, что
   параметризация не меняет сложность).
4. **Калибровка β**: сходимость `BetaStat` к эмпирической сложности.
5. **Релевантность подбора**: размеченный вручную набор 20 пар
   «потребность × 50 кандидатов» → Precision@5, nDCG@10; отчёт
   объяснимости (глазами проверяем адекватность факторов).
6. **Пересечение наборов заданий** между сессиями (антислив, §7.4.4).

### 9.3. Пороги приёмки (фиксируем до прогона)

- Стабильность: ≥ 80% точного совпадения, ≥ 97% в ±1.
- Дискриминативность: Spearman(θ_true, θ_est) ≥ 0.85; соседние грейды
  путаются < 15% случаев.
- Подбор: Precision@5 ≥ 0.8 на размеченном наборе.
- Результаты — таблицей в документацию и 2 слайда в презентацию.

## 16. Критерии приёмки (проверяемые)

1. `docker compose up -d --build` на чистой машине → сквозной сценарий
   §1 проходится за 10 минут по README без посторонней помощи.
2. Приглашение без вилки ЗП отклоняется API (400); контакты кандидата в
   JSON работодателя отсутствуют до accept (тест).
3. Два старта теста одним кандидатом дают разные экземпляры заданий;
   смена грейда раньше кулдауна — 409.
4. Кандидат без истории ФСП: профиль и подборка корректны, блок
   достижений отсутствует (тест + скрин в документации).
5. Валидация §9 прогнана, пороги §9.3 выполнены, отчёт в
   `deliverables/validation/`.
6. Подборка по потребности содержит explanation у каждого кандидата.
7. OpenAPI-доки backend доступны (`/docs`), методы с примерами и кодами
   ошибок.
8. Экспресс-тест (§7.4.2) проходится за 3–5 минут «чужим» человеком без
   подсказок; вход через мок-FSP ID работает и подтягивает достижения.
9. Все пункты чек-листа §13 отмечены и показаны в видео/на защите.

- **Песочница/прокторинг/антиплагиат — плюс**, не MVP: code-исполнение
  деприоритизировано — §7.4.1.
- **LLM — облачные допустимы, включая зарубежные** (письменно 07.10);
  предпочтительны открытые модели; использование описать; ПДн не
  отправляем — §3.4, §12.
- **Вход через FSP ID — ожидаемый сценарий** (возможно, станет
  обязательным): мок-OIDC в fsp_registry — §5.3, §7.1.

- **Регулярные задания**: пишет работодатель; эталон — проверяет

### 18.3. Письменные ответы организаторов (07.10, xlsx в materials/)

Получены и влиты (`materials/Ответы на вопросы трек ФСП ЛЦТ__.xlsx`,
17 вопросов). Решения:

- **LLM**: облачные допустимы, в том числе зарубежные; предпочтительнее
  открытые модели; ПДн в модель — риски команды (у нас сняты §3.4).
- **Грейд = уровень навыков по тесту, не стаж**; стаж — атрибут
  профиля; «официально» грейд только по тесту — §6.
- **Широта справочника не поднимает оценку**: 2 спец × 2 грейда
  достаточно, механика важнее — §6, §10 (банк сокращён до ≥ 45).
- **Категория = spec + грейд достаточно**; несколько категорий у
  кандидата — плюс, не MVP — §6.
- **ФИО и места работы показывать допустимо**: скрыты только контакты —
  §7.2, §7.3 (анонимность — опция, не дефолт).
- **Неподтверждённый грейд — статус, грейд присваивается только
  тестом** — подтверждён наш дизайн §6/§7.5.2; антисписывание — плюс
  (у нас таймлимиты + уникальные экземпляры, §7.4.4).
- **Валидация test-retest + разделяющая сила, симуляция на синтетике
  допустима** — в точности наш §9 (реализован, PASS).
- **Регулярные задания адресные**, челлендж на категорию не запрещён,
  способ оценки — на команде — §7.8.
- **Достижения ФСП**: буст внутри грейда, дисциплины равны; идея
  релевантности дисциплины специализации — опционально — §7.9.
- **Питч 10 минут; видео вместо живого стенда допустимо; стенд держать
  во время оценки** — §14.
- **Лимитов на размер образа/вес моделей/RAM нет** — §12; качество
  подбора важнее скорости — §12.
- **ATS = синхронизация вакансий/откликов/статусов через API** —
  концепция зафиксирована в §13.
- **Дизайнеры**: справочник может включать, но MVP — технические роли —
  §6.
